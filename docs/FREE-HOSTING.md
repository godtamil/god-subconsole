# Free online website: Render + Neon

This project can use Render's Free Node web-service plan and Neon's Free PostgreSQL plan, within their limits. It is not deployed yet. You need your own hosting accounts. Do not upgrade or add a paid database to follow this guide.

Render provides an HTTPS `onrender.com` website address and supports WebSockets. Free web services sleep after 15 minutes with no inbound HTTP/WebSocket traffic and can take about a minute to wake. Their local filesystem is ephemeral, so accounts must be stored in an external database. The Blueprint explicitly requests `plan: free` and creates no Render database or persistent disk.

Neon's current Free plan is $0, requires no credit card, and includes 1 GB storage and 100 CU-hours monthly per project. Active console sessions keep querying the database, so continuous monitoring can exhaust a free compute allowance. Treat this as free hosting within usage limits, not guaranteed unlimited 24/7 hosting. Keep both accounts on their Free plan and check their usage dashboards.

## Publish

1. Sign in to [Neon](https://console.neon.tech/), create a Free project, and copy its PostgreSQL connection string from the Connect dialog. Preserve its SSL requirements. Keep it private.
2. Put the project source in a private GitHub repository. Include `render.yaml` at the repository root. Never upload `.env`, `.data`, `node_modules`, or local credentials. The provided ZIP excludes these files.
3. Sign in to [Render](https://dashboard.render.com/), select New → Blueprint, and connect that repository. If GitHub adds an outer folder, set the service Root Directory to the inner `god-subconsole` folder where `package.json` and `render.yaml` live, or put that folder's contents at the repository root.
4. Check that the service plan is Free. Supply `DATABASE_URL` from Neon and `PTERODACTYL_CLIENT_API_KEY` in Render's protected environment fields. The other secrets are generated by the Blueprint. Do not paste those values into chat or source files.
5. Deploy. Migrations run at application startup. The app derives its public origin from Render's `RENDER_EXTERNAL_URL` automatically when `APP_URL` is not set. Render supplies the listening port; `HOST=0.0.0.0` allows its proxy to connect.
6. In Render's Environment panel, privately reveal/copy the generated `HOSTED_SETUP_TOKEN`. Open your deployed site with `/#setup=` followed by that token. Example shape only: `https://YOUR-SERVICE.onrender.com/#setup=YOUR-PRIVATE-TOKEN`. Choose your owner email and password yourself.
7. After creating the owner, remove `HOSTED_SETUP_TOKEN` from Render and redeploy. Owner creation is disabled once an owner exists, even if that token is presented again. Enable two-factor authentication in Account before management actions.
8. Test login, the resource row, full UUID/address copying, and console output. Use mocks for mutation tests; do not run automated power/file/command tests against the live server.

You can share the regular HTTPS website URL after setup. Never share the setup fragment/token. New sign-ups still have no server assignments until the owner approves them.

If using a custom website domain, add it in Render and set `APP_URL` to that exact HTTPS origin. The Minecraft game address `godtamilsmp.chickenkiller.com:25568` is separate from this website address.

## Optional services

Password recovery needs your own SMTP service, configured through Render's protected environment fields. Some free hosting plans restrict common SMTP ports, including Render Free; check the provider's current policy and use an allowed mail-service transport before enabling recovery. This deployment does not claim email delivery is configured.

This app retains resource history in memory; it resets on service restart/wake. Sessions, application accounts, settings, invitations, and audit records persist in Neon. Free quotas and provider policies may change. Deployment, remote PostgreSQL connectivity, HTTPS cookies, and the provider's proxy/WebSocket behavior still need verification after your account is connected.
